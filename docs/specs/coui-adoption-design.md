## 四、硬约束：版本链（决定"能不能引库"）

这不是偏好问题，是编译期就过不去的问题。`coui-ui-android:2.1.0` 的 POM 明确要求：

| 维度 | Branchbase 现状 | COUI 2.1.0 要求 | 结果 |
|---|---|---|---|
| Kotlin | **2.3.10**（`libs.versions.toml:3`） | `kotlin-stdlib **2.4.10**` | 元数据高一代，2.3 编译器直接拒绝读取 |
| Compose | BOM `2026.01.01` → `androidx.compose.foundation **1.10.2**` | `org.jetbrains.compose.foundation 1.11.1` → `androidx.compose.foundation **1.11.2**` | 同一个 artifact 两条版本线，必须整体上 BOM |
| AGP | 9.0.0（内置 KGP 2.2.10；compose 插件 2.3.10） | 未声明下限 | 升级链要一起验 |
| KSP | 2.3.10（Room） | —— | 随 Kotlin 一起动 |
| 附加依赖 | —— | `materialKolor 5.0.0`、`navigationevent 1.1.2`、`window-size-class` | 与本仓库自研返回栈/导航共存要验证 |

**这不是新发现 —— 本仓库已经为同一堵墙让过一次路。** `libs.versions.toml:29-31` 关于液态玻璃的注释：

> 版本只能停在 1.0.x：1.0.6 依赖 kotlin-stdlib **2.3.10**（= 本工程 Kotlin，元数据同代）+ androidx.compose **1.10.3**（本工程 BOM 给 1.10.2）；
> 2.0.x 换成 kotlin-stdlib **2.4.10** + Compose Multiplatform 1.12，**会要求升 Kotlin，属于另一件事**。

COUI 的情况更硬：它**没有任何一个版本**能配 Kotlin 2.3.10（1.0.0 起就是 2.4.10）。
所以"引库"的前置是一次**平台升级专项**（Kotlin 2.4 + Compose 1.11 + AGP/KSP 协同 + `:editor` 的 Sora Editor 兼容验证 + 5 渠道构建回归），
跟"要不要这个风格"是两件事，不能混在一个迭代里做。

## 五、风格适配度

### 5.1 设计令牌对照

| 令牌 | COUI 2.1.0 | Branchbase 现状 | 差异判断 |
|---|---|---|---|
| 主色 | `#3482FF`（ColorOS 蓝） | `#0969DA`（Primer 蓝） | **品牌级冲突**，见 §5.3 |
| 卡片圆角 | **24dp**（超椭圆，smoothing weight 2.5） | **10dp**（普通圆角 + 1dp 描边） | 观感差异最大的一项 |
| 行最小高 | 48dp（内边距 16/10） | 48dp（内边距 16，纵向 11–12dp） | **基本一致**，换皮不会破密度 |
| 页面边距 | 卡片距边 16dp、卡间距 16dp | 分组左右 12dp、组间 6dp | 需要重排 |
| 顶栏 | 折叠大标题 116dp / 40sp（设置首页） | 16sp 小标题 + 返回箭头（`SubPageHeader`） | 结构级差异 |
| 深色底 | `#000000` / 卡片 `#242424` | `#0D1117` / 卡片 `#161B22`（GitHub dark） | 色相不同 |
| 模糊 | 顶栏 / 弹层 / 菜单 / 按钮全模糊，Edge light | 仅底部玻璃导航；门槛 API 31 | 能力已有，门槛不同（33 vs 31） |
| 圆角形状 | 超椭圆（squircle） | 普通圆角 | 可单独吸收 |
| 动效 | 系统曲线 + 预测性返回 | 四弹簧 + 页面级/元素级两层（`Motion.kt` 538 行） | 已有体系，不要两套并存 |

> 口径提醒（取证于 2026-11-25）：`v2.1.0` 源码是 `CardDefaults.CornerRadius = COUIRoundCorner.Normal.XL`
> （= **24dp**，超椭圆），agent 指南也写 24dp；但文档站 `components/card.md` 写 **12dp**，
> 而**当前 main 分支已经改回 12dp**。
> 也就是说：**同一项视觉令牌在发布版、文档、主干之间三个口径**。真要引库必须锁版本读源码，
> 不能按文档写代码 —— 这也正好说明它的令牌还在漂移（见 §2 "experimental"）。

### 5.2 契合的地方（值得吸收）

1. **设置树**：12 个设置界面、6 种行型，与 COUI 的 `PreferenceCategory + Card + CardListGroup + SwitchPreference/ArrowPreference` 几乎是同构的 —— 这是全 App 最适合"卡片分组 + 分类标题"的地方。
2. **弹层（48 处）**：COUI 的"面板模糊 + 边缘高光"正是本仓库已经在底部导航上做过的事（kyant backdrop），能力现成，只是没用在 Dialog/Sheet 上。
3. **低频页面**：关于页、日志页、语言页、Git 代理页这类"内容少、停留短"的页面，放大标题不会伤信息密度。
4. **行高巧合**：48dp 对 48dp —— 说明"换观感不换密度"在设置页是可行的，不需要重排信息架构。

### 5.3 冲突的地方（不建议全量换的理由）

1. **品牌身份**：Primer 色板已作为 vendored 设计令牌登记在 `THIRD-PARTY-NOTICES.md` §一；换成 ColorOS 蓝后，与 GitHub 内容自带的语义色（issue 状态、语言色、贡献图）互相打架，GitHub 客户端会失去"这就是 GitHub"的第一眼识别。
2. **信息密度**：COUI 是系统设置页节奏（16dp 边距、24dp 卡片、116dp 大标题）；Branchbase 的主体是仓库列表、代码、diff、运行日志 —— 大圆角和大标题在这些页面是纯浪费。
3. **已有资产会作废**：液态玻璃导航（三层结构 + 四弹簧 + 11 条测试）与 1.4.11–1.4.16 刚做完的设置页高亮滑动/抽屉动效，换 COUI 等于全部推倒；而这两项恰好是本项目最像"自己的东西"的部分。
4. **测试钉子会红**：`ThemeContrastTest`（对比度阈值）、`ThemeConvergenceTest`（禁止写死颜色）、`SettingsSpecTest`（禁裸 `Row` 自制设置行）、`GlassBackdropTest` —— 全部要跟着改，等于把"防退化"的钉子拔了重钉。
5. **门槛不一致**：模糊 API 33，现有玻璃 API 31，`minSdk 24`。低版本用户会看到"一半玻璃、一半实心"的两套观感。
6. **依赖重量**：release 未开 R8，6.4 MB AAR + 若干传递依赖会近乎全额进包（当前 debug 已 38 MB）。

## 七、C 路线（现为实现手段）：借语言，不借库

> 2026-11-25 起，本节不再是一条独立的整体路线，而是**每个皮肤内部**的细节取舍原则 ——
> 多 UI 体系里仍然成立：皮肤之间的差异走令牌与组件分叉，皮肤内部不做无意义的重复造轮子。

### 7.1 三件事（按性价比排序）

**P0 · 设置树卡片化**
- 把 12 个设置界面的分组容器改成 COUI 语言：**24dp 圆角、去掉 1dp 描边（或降到极淡）、分类标题在上**（24dp 取 v2.1.0 口径；嫌胖可退 16dp）；
- **行型与行高不动**（6 种行型、48dp），信息架构不动；
- 改动集中在 `SettingsRow.kt` 的容器与 `SectionTitle`，页面只改外层包裹；
- 同步修订 `settings-design.md` §4（行的解剖）与 §9（令牌取舍），并让 `SettingsSpecTest` 继续拦裸 `Row`。

**P1 · 弹层材质**
- 做一个 `GlassPanel` 包装（复用 `ui/navigation/Backdrop.kt` + kyant backdrop），套到 48 处 `*Dialog(` / `*ModalBottomSheet(` 的面板上；
- 门槛沿用现有 **API 31**，不跟 COUI 的 33 走；圆角保持 16dp（弹层不要 24dp，会显胖）；
- 一次实现、分批替换，失败可单点回退。

**P2 ·（可选）低频页的大标题折叠**
- 只给关于 / 日志 / 语言 / 网络这类页面；仓库、代码、diff、运行日志保持紧凑标题；
- 复用 `Motion.kt` 的页面级弹簧，不引入第二套曲线。

### 7.2 明确不做

- 不改主色（`#0969DA` 是身份，不是装饰）；
- 不替换底部玻璃导航；
- 不引 COUI 依赖（`coui-*` 一个都不加）；
- 不把 40sp 大标题搬到信息密集页；
- 不做"主题风格：COUI / 原生"的切换器 —— 见 B 路线，维护不起。

### 7.3 验收（沿用现有钉子，不新造指标）

1. `ThemeContrastTest` / `ThemeModeTest` / `ThemeConvergenceTest` 全绿（新圆角/新容器不得引入写死色）；
2. `SettingsSpecTest` 全绿（行型封闭集合不被绕过）；
3. `GlassBackdropTest` 全绿（弹层复用 backdrop 不得污染导航采样层）；
4. 同一台设备、同一轮场景的 `FrameWatch` 对比：32ms 慢帧率不高于改动前（`frame-perf-design.md` 口径）；
5. 5 渠道构建通过 + 浅/深两套 × 中/英两语言的截图核对；
6. 记录 APK 体积增量（预期 ≈ 0，因为不加依赖）。

## 八、引库前置清单（多 UI 里的 COUI 皮肤适用）

按顺序做，任何一步不通过就停：

1. **平台升级专项**（独立迭代，不与风格混做）：Kotlin 2.4.x + Compose BOM 1.11.x + KSP/AGP 协同 + `:editor`（Sora Editor 0.23.6）+ `:translate` 回归 + 5 渠道构建；
2. **单页试点**：只挑一个低频页（如"关于"）用 COUI 重写，量 APK 增量、构建时长、`FrameWatch`；
3. **决策点**：试点若出现"两套材质同屏"或"依赖冲突"，回到 C；
4. **回滚方案**：COUI 只进独立模块，主 App 通过接口引用，删一行即可回退；
5. **合规**：`THIRD-PARTY-NOTICES.md` §二登记 Apache-2.0 + 上游仓库；
6. **监控**：COUI 处于 experimental，锁死版本、记录升级窗口，不跟随 `latest`。

> 记录范围**只到"决定做什么"**，不含实现方案；实现由后续会话另开任务，并按 §11.4 的底线验收。

### 11.1 决策原文（逐字保留）

> **决策一**：建立多 UI 体系建设兼容机制，单独在设置页面增加开关与配置单独页面
>
> **决策二**：UI切换时使用动效+过渡动画+过渡壁纸动画做切换效果；不生切，不硬切，不立刻替换；在相应的切换页面即可见到切换效果

### 11.2 解读（记录时的理解；标"待定"的尚未决定）

**D1 拆成三件事：**

1. **多 UI 体系**：皮肤（skin / 主题包）成为一等公民 —— 令牌（颜色 / 字体 / 圆角 / 间距 / 动效曲线）、组件视觉、导航 chrome、弹层材质，都要能按皮肤切换；
2. **设置页一个入口行**（2026-11-25 确认：是入口行，**不是开关**）：放在设置树「外观」分组下，右侧显示当前皮肤名，点击进入配置页；
3. **独立配置页**：皮肤相关配置集中到一个单独页面（选皮肤 + 每皮肤参数 + 过渡相关），不与现有设置项混排。

**D2 拆成三条硬约束 + 一条可观测要求：**

| 约束 | 含义（记录口径） |
|---|---|
| **不生切** | 切换是"过渡"而不是"赋值"：有明确的开始、过程、结束三态 |
| **不硬切** | 不能靠 `Activity.recreate()` / 重启进程 / 重进页面来换肤；不能靠一闪而过的重建 |
| **不立刻替换** | 旧皮肤内容**保留到过渡结束**才退场；不是新皮肤瞬间盖上去 |
| **效果就在切换页（仅配置页）** | 在配置页里选定皮肤后，**当场**演示过渡（含过渡壁纸动画），不跳转、不返回、不要求用户"去别处看看效果"；其他页面不做演示 |

**"过渡壁纸动画"的记录口径**：过渡期间的一层全屏视觉（壁纸/渐变/纹理/模糊），随过渡进度推进，
作为新旧皮肤之间的"幕布"；它属于过渡的一部分，不是可选的装饰（开关与否待定，见 §11.5）。

**两处表述已确认（2026-11-25 二次确认，取代记录时的两种读法）：**

| 原表述 | 确认结论 | 对实施的含义 |
|---|---|---|
| “设置页面增加开关” | **入口行**，不是总开关 | 设置「外观」下加一行（`NavRow`），右侧显示当前皮肤名；点进配置页。**不提供**“启用/关闭多 UI”的开关态 |
| “在相应的切换页面即可见到切换效果” | **只在配置页**演示 | 过渡动画只在配置页内触发与验收；其他页面不加换肤入口、不做演示；离开配置页即停止 |

> 推论（记录用）：过渡的**实现**可以放在共享层（将来复用不重写），但**验收面只在配置页**；
> 不要在仓库页 / 个人页 / 弹层里加“切换预览”之类的第二入口。

### 11.3 对现有架构的影响（成本重估）

**这次比上午估的便宜的地方：**

- 换色几乎零成本：`Primer.XXX` 是读 `LocalPrimerPalette` 的 `@Composable get()`（`ui/theme/Color.kt`），
  1747 处调用点**一行不用改**；换肤 = 换 `CompositionLocal` 提供的色板；
- 主题已是"色板 + 角色"两层（`ui-design.md` §2），天生就是换肤点；
- 动效已有两层体系（`Motion.kt` 538 行），过渡动画不必从零造。

**这次比上午估的贵的地方：**

- 组件视觉是**写死的常量**：48dp 行高、10dp 圆角、1dp 描边（`SettingsRow.kt:73,78`），令牌化才能按皮肤分叉；
- 页面 chrome 是手搓的（`TopAppBar(` / `Card(` 均为 0），皮肤一变，顶栏/卡片/弹层都要有对应实现；
- 测试矩阵翻倍：5 渠道 × N 皮肤 × 明暗两套，`ThemeContrastTest` 需要参数化；
- 包体与构建：多一套组件与资源，release 未开 R8，增量接近全额进包。

**COUI 皮肤的特殊约束不变**：仍受 §4 版本链限制（Kotlin 2.4.10 / Compose 1.11）。
两条路：先做平台升级专项再引库（§8），或者第一个皮肤先做成"COUI 风"的自研皮肤、把库留到第二步。

### 11.4 切换的技术底线（记录为验收约束，不是实现方案）

1. **不重建 Activity、不重启进程、不闪白屏**；
2. 旧皮肤内容保留到过渡结束，过渡结束才完成替换；
3. 过渡**可中断、可回退**；中断后状态一致（不能停在半新半旧）；
4. 滚动位置、输入内容、导航栈、弹层状态**不丢**；
5. 过渡期间输入不被长时间阻塞（阈值待定）；
6. 遵循系统"减弱动态效果 / 移除动画"设置，此时降级为快速淡入淡出（仍不得硬切）；
7. 低端机可降级（省掉壁纸动画与模糊），但**降级后仍是过渡**；
8. 切换完成后，新皮肤的首帧不得出现"颜色先对、圆角/字体后到"的分裂。

### 11.5 配置页要装什么（待定清单，记录用）

- 皮肤选择（列表 + 当前项；是否支持"跟随系统"待定）—— 设置页那一行只是入口，选择与参数都在本页；
- 过渡动效：播放开关（本页配置项，不是多 UI 总开关）/ 时长档位 / 是否播放壁纸动画；
- 每皮肤独有项（示例：COUI 风的模糊与 AMOLED 纯黑、玻璃风的折射强度、经典风的密度）；
- 就地预览区：在配置页内直接演示过渡（对应 D2 的"效果就在切换页"）；
- 与现有设置的关系：新增入口归入 `settings-design.md` 的两级 IA，**6 种行型仍是封闭集合**。

### 11.9 决策的可逆性

- 皮肤抽象层是"加一层"，不删现有 Primer / 玻璃导航 → 只保留一套皮肤时，行为与今天一致；
- 入口行与配置页可整体下线（删入口 + 保留默认皮肤），不牵动业务代码；
- COUI 皮肤若走引库路线，必须独立模块 + 接口引用，保证"删一行即回退"（§8 第 4 条）。
